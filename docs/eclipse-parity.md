# Eclipse 与 Omni 效果对照

本文件把 Eclipse（`references/Eclipse/shaders`，基于 Bliss 的改版）当作参考，逐类对照 Omni 现在能做什么、差在哪里、该不该合并。
它是只读调查的产物，不改任何代码；iterationT 的移植合同仍在 `docs/parity.md`，两者互不覆盖。
2026-10-17 按 `git log` 与当前 `main` 代码重写一次：把 `dev.127`–`dev.132` 新合并的一批 Eclipse 能力（后处理滤镜、体积雾体系、交互与细节、程序化草、环境与天气）从「未合并」移出并写清落点；随后按 `dev.133`–`dev.142` 的提交把状态与 `file:line` 同步到当前 `main`。

## 怎么读这份文档

- **第一列「效果」**：一类画面能力，例如月亮、体积云、水波。
- **第二列「Eclipse 的做法」**：Eclipse 侧的文件路径（相对 `references/Eclipse/shaders`）、关键函数名、它暴露给玩家的选项名和默认值。每个判断都带 `文件:行号`，行号来自文件真实内容。
- **第三列「Omni 现状」**：Omni 侧文件（相对 `shaders`）、函数、`OMNI_*` 选项与默认值。Omni 没有这项就写「无」。
- **第四列「差异与合并建议」**：先说状态，再给证据与差额。状态只有四种：
  - **已合并**：Eclipse 的算法（或同一套数学）已搬进 Omni，写清落点。
  - **近似**：能力在，但换了写法或只搬了一部分，写清差在哪。
  - **未合并**：Eclipse 这项在 Omni 没有对应，写清原因，并在括号里标是哪一类——`换来源`/`换模型`（Omni 用 iterationT 版本，能力在但不是 Eclipse 的）、`两套都留`（两边各有一套，都保留）、`技术上不可行`、`需要跨程序结构改动`、`按项目规则不写模组专用适配`。
  - **保持 Omni 现状**（并进「未合并」计数）：两边都有等价能力，但 Eclipse 的具体参数或做法没有搬，Omni 保留 iterationT 版本。

**怎么用它决定合并顺序**：先只读第四列。标着「已合并」或「近似」的已完成；「未合并」的按原因分类，`换来源`/`换模型`/`两套都留` 一般不必再动，`技术上不可行`/`需要跨程序结构改动` 才需要评估新方案。

**看之前先知道两件事**：

- Omni 现在的效果是一比一移植 iterationT 3.2.0（`docs/parity.md`），Eclipse 是另一套实现。所以很多「差异」不是缺功能，而是换了算法来源。这一列会写清属于哪种。
- 结构不同：Eclipse 在 `dimensions/` 放共享实现，`world0/`、`world-1/`、`world1/`、`world0_with_aether_flag/`、`world0_with_twilight_forest_flag/` 是薄包装（此结构判断未逐行确认）；Omni 用 `rendering/` 放绘制主体，`world*/` 是薄入口。
